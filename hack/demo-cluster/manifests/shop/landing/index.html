kubectl-probes demo cluster

A three-node kind cluster running a small system, so the plugin has something real to read. This page is the front door — it explains what the other pages are showing you.

What happens when you load a page here

Your browser asks for shop.localtest.me:8080
/etc/hosts → 127.0.0.1 your router blocks the public record, so the name is resolved locally
colima → kind nodeport 8080 → 80 the cluster runs as containers inside a small Linux VM
ingress-nginx picks the Service by the Host header you sent
Service shop/web2 pods balances across two identical pods — which is why the pod name on that page changes when you refresh
Service shop/api2 pods web calls this itself, inside the cluster, to render its page

Reading the podinfo pages

web and api are podinfo: a small Go app built to be a test workload for Kubernetes. It does nothing useful on purpose. What it has is real health endpoints, and the ability to call a backend and draw the chain.

The cuttlefishpodinfo's logo. Decoration, nothing more.

The services

web → the frontend, calling api api → the backend, on its own Grafana → anonymous, Prometheus wired up Prometheus → scraping the cluster

Also running, with no page to visit: catalog, postgres, redis, a backup CronJob, and node-exporter on every node.

Now point the plugin at it

kubectl probes -A                    # every workload in the cluster
kubectl probes -n shop               # just the shop
kubectl probes -n shop deploy/web    # one workload, in detail

Every workload here has deliberate probe configuration. web and grafana are configured well and report nothing. The rest each demonstrate something: a missing readiness probe, a liveness probe that restarts before readiness removes, a timeout longer than its own period.

Break something on purpose

make chaos    # then reload this page and run kubectl probes again
make heal     # put it back

catalog's liveness probe starts failing, so the kubelet restarts it on a loop — restart counts climb and the evidence names the probe.

web is the sly one. Breaking its readiness probe starts a rolling update whose new pod never becomes ready, so the rollout stalls and the old pods carry on serving. This page keeps working, nothing restarts, and from outside the deployment looks fine. The plugin reports 2/3 ready and marks the column with *: the running pods no longer match their own template.
